## 1. ทำอะไรเสร็จแล้ว

- โครงระบบ: Next.js 16 (หน้าเว็บ `src/`) + Express (API `server/`, ที่ `/api/v1`) รันใน process เดียวผ่าน `server.js`
- ฐานข้อมูล: Drizzle ORM + mysql2, schema ที่ `db/schema.ts`, migrations ที่ `db/migrations/` (รันอัตโนมัติตอน server เริ่ม)
- ตาราง: ส่วนงาน, สถานที่, ประเภทอุปกรณ์, อุปกรณ์, แผนบำรุงรักษา, ใบงาน (+ `app_meta`)
- หน้าจอ: Dashboard แบบ Bento, ทะเบียนอุปกรณ์ (ค้นหา/กรอง/จัดเรียง/แบ่งหน้าที่ฝั่ง server)
- ธีมมืด (ค่าเริ่มต้น) และสว่าง, ฟอนต์ LINE Seed Sans TH ทั้งเว็บ
- ข้อมูลสมมติสำหรับพัฒนา: `npm run db:seed` (20 อุปกรณ์, 81 ใบงาน) ไม่รันบน production
- push เข้า git และ GitHub Actions deploy ขึ้นโฮสต์สำเร็จแล้ว (ไฟล์ขึ้นถึง `apps/equiplog/`)
- ระบบ login (CMU OAuth + บัญชีในเครื่อง), บทบาท, QR, รูป, บันทึกงานซ่อม, เพิ่มอุปกรณ์, ข้อมูลหลัก: push แล้วทั้งหมด (ดูหัวข้อ 1.1–1.11)

## 1.10 เพิ่มอุปกรณ์ จัดโฟลเดอร์รูปตามส่วนงาน (push แล้ว)
- ปุ่ม "เพิ่มอุปกรณ์" ในหน้าทะเบียน (เฉพาะ Super Admin และช่างเทคนิค) เปิด popup กรอกข้อมูล → หน้ายืนยัน → บันทึก; ระบบเสนอรหัสถัดไป (เช่น AC-ENG-004) แก้เองได้ รหัสซ้ำจะแจ้งเตือน; QR สร้างให้อัตโนมัติ
- ช่างที่ login ด้วย CMU เพิ่มได้เฉพาะส่วนงานของตัวเอง (ตรวจที่เซิร์ฟเวอร์)
- รูปอุปกรณ์เก็บใต้ `assets/<รหัสส่วนงาน>/<id>` (migration 0008 จะรันตอน restart) และย้ายตามเมื่อเปลี่ยนส่วนงาน
- ตัวกรองส่วนงานไม่แสดงรากมหาวิทยาลัย (ซ้ำกับ "ทุกส่วนงาน"); ลบไอคอนดินสอ; QR+ประแจย้ายไปคอลัมน์แรก
- เมนู "ข้อมูลหลัก" (เฉพาะ Super Admin): จัดการส่วนงาน (เป็นต้นไม้), ประเภทอุปกรณ์, สถานที่ (วิทยาเขต/อาคาร/ชั้น/ห้อง) — เพิ่ม แก้ชื่อ/ที่อยู่ภายใต้ ลบ (ปุ่มแก้ไข/ลบเป็นไอคอนล้วน); รหัสแก้ไม่ได้หลังสร้าง; ไม่มีปุ่ม "เก็บถาวร" แล้ว (ผู้ใช้สั่งเอาออก); ลบไม่ได้ถ้ายังมีอุปกรณ์/รายการย่อย/ผู้ใช้ใช้อยู่ (API `/master/:kind`, ทดสอบ 56 รายการ)
- ปุ่ม "ลบ" (ถาวร, มีหน้ายืนยัน) ใช้ได้เฉพาะรายการที่ไม่มีอุปกรณ์/รายการย่อย/ผู้ใช้อ้างอิง
- ลบหน่วยราก "มหาวิทยาลัยตัวอย่าง" ออกจากข้อมูลสาธิตทั้งหมด (seed, demo-data.sql, DB เครื่องนี้) คณะ/สำนักเป็นระดับบนสุด ถ้าโฮสต์เคยนำเข้าข้อมูลสาธิตเดิมไว้ ต้องลบแถวนี้บนโฮสต์ด้วย (ดูคำแนะนำตอน push)

## 1.9 หน้าภาพรวม และการรองรับอุปกรณ์/เบราว์เซอร์ (push แล้ว)

- หน้าภาพรวม: เอาตัวกรอง "ตั้งแต่วันที่/ถึงวันที่" ออกแล้ว (งานเสร็จสิ้นและค่าใช้จ่ายนับย้อนหลัง 12 เดือนโดยอัตโนมัติ); dropdown "ส่วนงาน" ยาวกว่าช่องอื่นและเน้น (ตัวหนา กรอบสีม่วงบาง ๆ พื้นหลังทึบเดิม เพื่อให้รายการที่เปิดลงมาไม่เป็นสีเทาในธีมมืด); จอ ≥1280px วางเรียงแถวเดียว จอเล็กกว่านั้นให้ช่องส่วนงานเต็มแถว
- **กล่อง "รายการใกล้ครบกำหนดและเกินกำหนด" และ "กิจกรรมล่าสุด" คลิกได้ทั้งแถว**: ช่างและ Super Admin → เปิดอุปกรณ์พร้อมฟอร์มบันทึกงานของแผนนั้น (`?plan=<id>`) หรือฟอร์มของใบงานนั้น (`?job=<id>`) ทันที (ถ้าอุปกรณ์มีงานค้างจะให้เลือกก่อน); ผู้ชม → เปิดหน้าอุปกรณ์เฉย ๆ; พารามิเตอร์ถูกลบออกจาก URL หลังเปิด รีเฟรชแล้วไม่เปิดซ้ำ
- **การรองรับ**: ตรวจเค้าโครงที่ความกว้าง 320–2560px ทั้งแถบเมนูขยาย/หุบ บนหน้า ภาพรวม, ทะเบียนอุปกรณ์, รายละเอียดอุปกรณ์, login (ไม่มีแถบเลื่อนแนวนอน เนื้อหาเต็มพื้นที่) แก้ปัญหาที่พบ: `URLSearchParams.size` (ต้องใช้ Safari 17+/Chrome 113+ ถ้าไม่มีตัวกรองและการเปลี่ยนหน้าจะหายเงียบ ๆ) ใช้ `toString()` แทน; หน่วย `dvh` มี fallback เป็น `vh` สำหรับ iOS Safari <15.4 / Chrome <108 (`globals.css`)
- **ฐานของเบราว์เซอร์ที่รองรับ = ตามข้อกำหนดของ Tailwind CSS v4/Next.js 16**: Chrome/Edge 111+, Safari/iOS 16.4+, Firefox 128+ (เบราว์เซอร์เก่ากว่านั้นสีและเงาบางส่วนจะเพี้ยน) **ทดสอบจริงเฉพาะ Chrome** ส่วน Safari/Firefox/มือถือจริงตรวจจากโค้ด ไม่ได้ทดสอบ
- ระวัง: ข้อความท้ายหน้าภาพรวมยังเขียนว่า "ข้อมูลทั้งหมดเป็นข้อมูลสมมติเพื่อทดสอบระบบ" ควรเอาออกก่อนใช้ข้อมูลจริง

## 1.8 แถบเมนู ปุ่ม burger และไอคอนผู้ใช้ (push แล้ว)

- แถบเมนูด้านซ้ายหุบได้: ปุ่ม burger มาตรฐาน (ขีดสามเส้น) อยู่ต่อท้าย "CMU Asset" ชิดขอบขวาของแถบ; เมื่อหุบ แถบเหลือกว้าง 76px แสดงเฉพาะไอคอน (ชื่อเมนูเป็น tooltip) **ปุ่ม burger หายไป และใช้ไอคอนประแจสีม่วง (โลโก้) เป็นปุ่มขยายเมนูแทน** จดจำสถานะไว้ในเบราว์เซอร์ (`localStorage` คีย์ `sidebar`)
- **เนื้อหาเต็มพื้นที่ที่เหลือข้างแถบเมนูทั้งตอนขยายและตอนหุบ** (เพดานเดียว 1800px จัดกึ่งกลางเฉพาะจอกว้างมาก; เดิมจำกัดไว้ 1240px ทำให้เหลือที่ว่างด้านขวาตอนขยายเมนู)
- มือถือ (<1024px): ไม่มีแถบข้าง ปุ่ม burger ใน header เปิดเมนูเป็น dropdown เหมือนเดิม
- ไอคอนผู้ใช้แบบ minimal (SVG วาดเอง ใช้ `currentColor` ตามธีม) ในวงกลมสีอ่อนข้างชื่อผู้ใช้ใน header ทุกขนาดจอ และเป็นไอคอนของเมนู "ผู้ใช้งาน" (`src/components/ui/user-icon.tsx`)

## 1.7 บันทึกงานซ่อมบำรุง (push แล้ว)

- **เฉพาะ Super Admin และช่างเทคนิคเท่านั้น** ที่บันทึก/แก้ไขได้ (Viewer ดูประวัติได้อย่างเดียว ไม่เห็นปุ่ม และ API ตอบ 403)
- ปุ่ม "บันทึกงานซ่อมบำรุง" ที่หน้ารายละเอียดอุปกรณ์ (หัวการ์ด "ประวัติงาน") และไอคอนประแจท้ายแถวในตารางทะเบียนอุปกรณ์ → popup (ฉากหลังเบลอ/มืด) กรอก: ประเภทงาน, หัวข้อ, สถานะงาน, วันที่ดำเนินการ, กำหนดเสร็จ, ความสำคัญ, แผนบำรุงรักษา, รายละเอียด/ผล, ค่าแรง/อะไหล่/อื่นๆ, และเปลี่ยนสถานะอุปกรณ์ในครั้งเดียว (เช่น ซ่อมเสร็จ → ปกติ) → หน้ายืนยัน → บันทึก
- ไอคอนดินสอท้ายแต่ละรายการประวัติ = แก้ไข/บันทึกผลของงาน (กำลังดำเนินการ → เสร็จสิ้น) งานที่เสร็จสิ้นแล้วเปลี่ยนสถานะกลับไม่ได้ แต่แก้รายละเอียด/ค่าใช้จ่ายได้
- เมื่อบันทึกงานที่ "เสร็จสิ้น" และเชื่อมกับแผน ระบบเลื่อน `next_due_date` ของแผนให้อัตโนมัติ (วันที่ดำเนินการ + ช่วงรอบ; ไม่เลื่อนถอยหลัง จึงบันทึกย้อนหลังได้ปลอดภัย)
- เลขใบงาน `WO-<ปี>-<4 หลัก>` สร้างอัตโนมัติ; เก็บผู้บันทึก (`work_orders.created_by`, migration `0006`) และแสดง "บันทึกโดย ..." ในประวัติ
- ค่าใช้จ่ายเว้นว่าง = ไม่ทราบ, 0 = ไม่มีค่าใช้จ่าย (ไม่นับเป็น 0 บาทในรายงาน)
- **สถานะงานมีแค่ 2 อย่าง: "กำลังดำเนินการ" และ "เสร็จสิ้น"** (migration `0007`: งานเดิมที่เป็น เปิดงาน/มอบหมาย → กำลังดำเนินการ; ยกเลิก → เสร็จสิ้น พร้อมเติมหมายเหตุ "[สถานะเดิม: ยกเลิก]" ไม่มีข้อมูลถูกลบ; API ปฏิเสธสถานะอื่น)
- **สถานะอุปกรณ์เชื่อมกับงานอัตโนมัติ ใช้คำเดียวกัน "กำลังดำเนินการ"** (ป้าย `under_repair` เดิมเรียก "อยู่ระหว่างซ่อม"; ป้ายสถานะอุปกรณ์ `active` เรียกสั้น ๆ ว่า "ปกติ"; ป้ายทั้งหมดอยู่ที่ `ASSET_STATUS_LABEL` ใน `shared/index.ts` ที่เดียว) กฎดูจากงานที่มีอยู่หลังบันทึก (`autoAssetStatus`): มีงานกำลังดำเนินการ → อุปกรณ์เป็น "กำลังดำเนินการ"; ไม่เหลืองานกำลังดำเนินการและอุปกรณ์เป็น "กำลังดำเนินการ" → "ปกติ"; หยุดใช้งาน/จำหน่ายออกไม่ถูกแตะ; "ชำรุด" เป็นสถานะที่คนตั้งเอง
- **กันตั้งสถานะที่ขัดกับงาน** (`assetStatusProblem`): ตั้งอุปกรณ์เป็น "กำลังดำเนินการ" เองไม่ได้ถ้าไม่มีงานกำลังดำเนินการ; ตั้งเป็น "ปกติ/ชำรุด" ไม่ได้ขณะมีงานกำลังดำเนินการ (ทั้งในฟอร์มบันทึกงานและฟอร์มแก้ไขอุปกรณ์ — ตัวเลือกที่ขัดกันกดไม่ได้ และ API ปฏิเสธ 400)
- **ตอน server เริ่ม ระบบแก้ข้อมูลที่ขัดกันอยู่แล้วให้เอง** (`reconcileAssetStatuses` ใน `server/startup.ts`, รันซ้ำได้ปลอดภัย) เช่นหลังนำเข้าข้อมูลด้วย SQL
- กดประแจ/"บันทึกงานซ่อมบำรุง" ที่อุปกรณ์ซึ่งมีงานค้างอยู่ จะขึ้นรายการงานค้างให้เลือก "บันทึกผล / แก้ไข" ก่อน (กันสร้างงานซ้ำ) หรือเลือก "เพิ่มงานใหม่"; หน้ารายละเอียดส่งงานที่ยังไม่เสร็จมาครบเสมอ (เรียงไว้บนสุด) ไม่ใช่แค่ 10 รายการล่าสุด
- หน้ารายละเอียดอุปกรณ์มีปุ่ม "แก้ไขข้อมูล" (หัวการ์ด "ข้อมูลอุปกรณ์") เปิดฟอร์มเดียวกับการแก้ไขในตาราง (เลขครุภัณฑ์เดิม วันประกันหมด ฯลฯ ยกเว้นรหัส)
- กันแก้ทับกันด้วย "เวอร์ชันจากเนื้อหา" เหมือนการแก้ไขอุปกรณ์ (409 ถ้ามีคนบันทึกไปก่อน)
- ยังไม่มี: หน้ารวมใบงานทั้งระบบ (เมนูล่วงหน้า "งานบำรุงรักษา เร็วๆ นี้" ถูกลบออกจากแถบเมนูแล้ว ค่อยเพิ่มเมื่อทำหน้านี้), การเพิ่ม/แก้แผนบำรุงรักษาจาก UI, ประวัติการแก้ไข (audit log)

## 1.6 รูปภาพอุปกรณ์ (push แล้ว)

- **1 รูปต่ออุปกรณ์, ไฟล์ที่เก็บไม่เกิน 1 MB, ชนิด JPG/JPEG/PNG เท่านั้น** (`MAX_IMAGES_PER_ASSET`, `IMAGE_MAX_BYTES` ใน `shared/index.ts`) การ์ด "รูปอุปกรณ์" ใต้ชื่อในหน้ารายละเอียด: คลิกดูรูปใหญ่; ปุ่ม "เพิ่มรูป" → "เปลี่ยนรูป" (รูปใหม่บันทึกสำเร็จก่อน ค่อยลบรูปเดิม) และ "ลบรูป" (ต้องยืนยัน); ทุกคนที่ดูอุปกรณ์ได้ดูรูปได้ ส่วน**เพิ่ม/เปลี่ยน/ลบเฉพาะ Super Admin และช่างเทคนิค** (Viewer ไม่เห็นการ์ดถ้าไม่มีรูป)
- ชนิดไฟล์อื่น (WebP, GIF, HEIC, PDF ฯลฯ) ถูกปฏิเสธทั้งหน้าเว็บและ server (ตรวจจากไบต์จริง ไม่เชื่อชื่อไฟล์) ไฟล์ต้นฉบับใหญ่ได้ถึง 25 MB เบราว์เซอร์ย่อให้เหลือ ≤1 MB (ด้านยาว ≤1600px JPEG; หมุนตามกล้องมือถือ; ตัด GPS/EXIF) จึงไม่ต้องใช้ไลบรารีฝั่ง server; ถ้าอยากให้ปฏิเสธไฟล์ต้นฉบับที่เกิน 1 MB แทนการย่อ แก้ที่ `MAX_PICKED_BYTES` ใน `src/lib/image-resize.ts`
- กันอัปโหลดซ้อนกัน: ล็อกแถวอุปกรณ์ตอนนับ/บันทึก (ส่ง 2 ครั้งพร้อมกัน สำเร็จ 1 ครั้ง ไม่มีไฟล์กำพร้า); server ตั้งชื่อไฟล์สุ่มเอง, เสิร์ฟพร้อม `nosniff` และ `Cache-Control: private, no-cache` (เบราว์เซอร์ถามทุกครั้ง → ตรวจ login/ส่วนงานทุกครั้ง ได้ 304 ถ้าไม่เปลี่ยน ไม่โหลดซ้ำ)
- **ไฟล์เก็บบนดิสก์ แยกโฟลเดอร์ตามคณะ/ส่วนงานเจ้าของอุปกรณ์**: `UPLOAD_DIR/assets/<รหัสส่วนงาน>/<รหัสอุปกรณ์>/<ชื่อสุ่ม>.jpg` (+ `_t.jpg` รูปย่อ) เช่น `assets/DEMO-A/12/` ชื่อโฟลเดอร์ส่วนงานใช้รหัสส่วนงาน (`organization_units.code`) เฉพาะ A-Z a-z 0-9 _ - ถ้ารหัสไม่มีตัวอักษรที่ใช้ได้ (เช่นเป็นภาษาไทยล้วน) ใช้ `unit-<id>` แทน; ตาราง `asset_images` เก็บโฟลเดอร์จริงของแต่ละรูปไว้ (คอลัมน์ `dir`, migration `0005` + `0008`) จึงเปลี่ยนรหัสส่วนงานทีหลังแล้วรูปไม่หาย; **ย้ายอุปกรณ์ไปส่วนงานอื่น → ไฟล์รูปย้ายตามไปโฟลเดอร์ของส่วนงานใหม่** (ถ้าย้ายไม่สำเร็จ ย้อนคืนและรูปอยู่ที่เดิมต่อ ไม่หาย); โฟลเดอร์ว่างถูกลบเอง; โฟลเดอร์ `assets/<รหัสอุปกรณ์>` แบบเดิมยังเปิดได้ ในเครื่อง `UPLOAD_DIR` คือ `./uploads` (git ไม่เก็บ)
- ความเร็ว/โควต้า: เปิดรูปจาก path ตรง ๆ ไม่ไล่ดูรายชื่อไฟล์ จึงไม่ช้าแม้มีหลายหมื่นรูป; ข้อจำกัดจริงคือโควต้าดิสก์และจำนวนไฟล์ (inode) ของโฮสต์ (รูปละประมาณ 3 รายการ, ~0.2–0.5 MB) และเวลาสำรองข้อมูล — ถ้าส่วนงานเดียวมีอุปกรณ์เกินหลักหมื่นค่อยแบ่งชั้นเพิ่ม
- **บนโฮสต์ต้องตั้ง `UPLOAD_DIR` เป็นโฟลเดอร์นอกโฟลเดอร์แอป** เช่น `/home/equiplog/equiplog-uploads` เพราะ deploy ผ่าน FTP จะลบไฟล์ทุกอย่างในโฟลเดอร์แอปที่ไม่ได้อยู่ใน build ถ้าไม่ตั้ง การอัปโหลดจะปิด (ตอบข้อความว่ายังไม่ได้ตั้งค่า) ไม่ทำให้รูปหายเงียบๆ
- รูปไม่อยู่ในฐานข้อมูล: การ Export จาก phpMyAdmin **ไม่รวมรูป** ต้องสำรองโฟลเดอร์ `UPLOAD_DIR` แยก และดูโควต้าพื้นที่ของโฮสต์ด้วย

## 1.5 หน้ารายละเอียดอุปกรณ์บนมือถือ (push แล้ว)

- บนจอกว้างน้อยกว่า 640px **ซ่อนกรอบ QR Code** (มือถือคือเครื่องที่สแกนอยู่แล้ว) จอใหญ่และตอนพิมพ์ยังแสดง
- "ประวัติงาน (10 รายการล่าสุด)" จัดใหม่: มือถือเป็นการ์ดต่อรายการ (ชื่องาน + ป้ายสถานะมีสี+ข้อความ / เลขใบงาน + ประเภท + ความสำคัญ / วันที่) จอใหญ่เป็นแถวแบบตารางมีหัวคอลัมน์ วันที่ | งาน | สถานะ (ใน `src/components/assets/asset-detail-view.tsx`)

## 1.4 บทบาทและหน้าผู้ใช้งาน (push แล้ว)

- บทบาทมี 3 อย่าง เรียงลำดับ: ผู้ดูแลระบบ (super_admin) → ช่างเทคนิค (technician) → ผู้ชมข้อมูล (viewer) — **ลบบทบาท "ผู้ดูแลส่วนงาน" (unit_admin) แล้ว** ทั้งในโค้ดและฐานข้อมูล (migration `0004` ย้ายผู้ที่ยังถือบทบาทนี้ไปเป็นผู้ชมข้อมูลก่อนลบค่าออกจาก enum)
- หน้า `/users`: เรียงผู้ดูแลระบบไว้บนสุดเสมอ แล้วตามด้วยช่างเทคนิค ผู้ชมข้อมูล (ภายในกลุ่มเรียงตามชื่อ); ปุ่ม "เพิ่มผู้ใช้" เปิด popup (ฉากหลังเบลอ/มืด) แทนกรอบฟอร์มเดิม; ปุ่ม "ตั้งรหัสผ่านใหม่" เปิด popup ที่ซ่อนรหัสเป็นจุด มีปุ่มรูปดวงตาเพื่อดู และมีช่องพิมพ์ซ้ำกันพิมพ์ผิด (`src/components/ui/password-input.tsx`)
- เอาช่อง "ผู้ขาย" และ "ราคา" ออกจากฟอร์มแก้ไข หน้ารายละเอียด และ API แล้ว (คอลัมน์ `vendor`, `price` ใน `assets` ยังอยู่ในฐานข้อมูล แต่ไม่ได้ใช้งาน)

### ทดสอบสแกน QR ด้วยมือถือตอน dev

1. มือถือกับคอมพิวเตอร์ต้องอยู่ Wi-Fi เดียวกัน (ถ้าเป็นเครือข่ายที่แยกอุปกรณ์ออกจากกัน เช่นบางแห่งในมหาวิทยาลัย จะไม่ผ่าน)
2. ดู IPv4 ของ Wi-Fi ด้วย `ipconfig` แล้วใส่ใน `.env.local`: `SITE_URL=http://<IP ของเครื่อง>:3000`
3. รีสตาร์ท `npm run dev` (ต้องรีสตาร์ทเพราะแก้ `next.config.mjs` เพิ่ม `allowedDevOrigins` สำหรับ IP ในวง LAN แล้ว)
4. อนุญาต Node.js ผ่าน Windows Firewall (เครือข่าย Private) ถ้า Windows ถาม
5. QR ที่บันทึกไว้ก่อนหน้า (เป็น localhost) ใช้ไม่ได้ ต้องเปิดดู/บันทึกใหม่หลังตั้ง `SITE_URL`

## 1.3 แก้ไขอุปกรณ์จากตารางทะเบียน (push แล้ว)

- ดับเบิลคลิกที่แถวในตาราง (หรือกด Enter ที่แถว; ไม่มีปุ่มดินสอในตารางแล้ว บนจอสัมผัสใช้ปุ่ม "แก้ไขข้อมูล" ในหน้ารายละเอียดอุปกรณ์) → popup กลางจอ ฉากหลังเบลอและมืด (`src/components/ui/modal.tsx`, `src/components/assets/asset-edit-dialog.tsx`)
- แก้ได้ทุกช่องยกเว้น **รหัส** (ล็อกทั้งหน้าจอและ API: ส่ง `code` มาจะถูกปฏิเสธ 400)
- กด "ตรวจสอบและบันทึก" → หน้ายืนยันแสดงค่าเดิม → ค่าใหม่ → ต้องกด "ยืนยันและบันทึก" ถึงจะเขียนฐานข้อมูล (ก่อนยืนยัน DB ไม่เปลี่ยน; "กลับไปแก้ไข" เก็บค่าที่แก้ไว้)
- สิทธิ์: Super Admin และช่างเทคนิคเท่านั้น (Viewer แก้ไม่ได้ ไม่เห็นปุ่ม และ API ตอบ 403); ช่างที่เข้าด้วย CMU แก้ได้เฉพาะอุปกรณ์ในส่วนงานตัวเอง และย้ายอุปกรณ์ไปส่วนงานอื่นที่มองไม่เห็นไม่ได้
- กันแก้ทับกัน: API เทียบ "เวอร์ชันจากเนื้อหา" (แฮชของฟิลด์ที่แก้ไขได้) ภายใน transaction ถ้ามีคนบันทึกไปก่อนจะตอบ 409 และให้ปิดแล้วโหลดใหม่
- Esc ปิด popup ได้เมื่อยังไม่ได้แก้อะไร ถ้ามีการแก้ค้างอยู่ต้องกด "ยกเลิก" เอง; คลิกฉากหลังไม่ปิด
- ยังไม่มี: ประวัติการแก้ไข (audit log) ว่าใครแก้อะไรเมื่อไร, การเพิ่มอุปกรณ์ใหม่, การสร้างประเภทอุปกรณ์/สถานที่จาก UI

## 1.2 QR Code ของอุปกรณ์ (push แล้ว)

- อุปกรณ์ทุกชิ้นมี `qr_token` สุ่ม 128 บิตของตัวเอง (คอลัมน์ใหม่ใน `assets`, migration `0003`); ระบบเติมให้เองตอน server เริ่ม (`ensureQrTokens` ใน `server/qr.ts`) จึงครอบคลุมอุปกรณ์เดิมและที่เพิ่มใหม่ทุกทาง
- QR เก็บ URL `<SITE_URL>/q/<token>` (ภาพ SVG ขาว-ดำเสมอ สร้างโดยไลบรารี `qrcode`) ดูได้ 2 ที่: (1) คอลัมน์ "QR Code" ท้ายตารางทะเบียนอุปกรณ์ — ภาพเล็ก เอาเมาส์ชี้ (หรือแตะ/โฟกัสด้วยคีย์บอร์ด) แล้วขยายใหญ่ พร้อมปุ่ม "บันทึก PNG" (มีรหัสและชื่ออุปกรณ์ใต้ QR) และ "SVG" ปิดด้วยเมาส์ออก/Esc/แตะที่อื่น (`src/components/assets/qr-cell.tsx`); (2) หน้ารายละเอียด `/assets/<id>` (ปุ่ม "พิมพ์ป้าย QR" ซ่อนเมนูตอนพิมพ์) — ไม่มีเมนู QR แยก (ลบแล้วตามที่สั่ง)
- สแกน → `/q/<token>` → **ต้อง login ก่อนเสมอ** (ยังไม่ login ถูกส่งไป `/login?next=...` แล้วกลับมาที่อุปกรณ์หลัง login ทั้งแบบ Username/Password และ CMU) → API ตรวจสิทธิ์ตามกฎเดียวกับข้อ 1.1: Super Admin และช่างเทคนิค (Username/Password) เห็นทุกส่วนงาน; คนที่ login ด้วย CMU เห็นเฉพาะอุปกรณ์ของส่วนงานตัวเอง (นอกส่วนงาน = 403 "อุปกรณ์นี้อยู่นอกส่วนงานของคุณ"; ไม่มีอุปกรณ์ = 404)
- สิทธิ์เดียวกันใช้กับ `GET /assets/:id` และภาพ QR (`/assets/:id/qr.svg`) ไม่ใช่แค่ตอนสแกน
- ป้องกัน open redirect: `next` รับเฉพาะ path ในเว็บเดียวกัน (`safeNextPath` ใน `shared/index.ts`)
- **QR ฝัง URL ตาม `SITE_URL` ตอนที่ภาพถูกสร้าง**: ในเครื่องเป็น `http://localhost:3000` ซึ่งสแกนด้วยมือถือไม่ได้ ก่อนพิมพ์ป้ายจริงต้องตั้ง `SITE_URL=https://equiplog.ddns.net` (หรือ IP ของเครื่องในวง LAN ถ้าจะลองสแกนด้วยมือถือตอน dev)

## 1.1 ระบบ login และสิทธิ์ (push แล้ว)

- login 2 แบบในหน้า `/login`: CMU Account (OAuth, เฉพาะ `@cmu.ac.th`) และ Username/Password พร้อม checkbox "จดจำฉัน" (ติ๊ก = อยู่ได้ **1 ปี** (`REMEMBER_DAYS = 365` ใน `shared/index.ts`; Chrome จำกัด cookie ไม่เกิน 400 วัน จึงตั้งเกินนี้ไม่ได้), ไม่ติ๊ก = หมดเมื่อปิดเบราว์เซอร์/สูงสุด 12 ชม.) session เก็บใน DB จึงรอดการรีสตาร์ท/deploy และใช้ได้ทุกอุปกรณ์/เบราว์เซอร์ (แต่ละเครื่องมี session ของตัวเอง) ถ้าเซิร์ฟเวอร์ตอบ error ชั่วคราวตอนเปิดเว็บ หน้าเว็บจะลองใหม่และขึ้นปุ่ม "ลองอีกครั้ง" แทนการเด้งไปหน้า login
  - ข้อจำกัดที่ควบคุมไม่ได้: ผู้ใช้ล้าง cookie/ข้อมูลเว็บ, โหมดไม่ระบุตัวตน, หรือเปิดลิงก์ QR ในเบราว์เซอร์ในแอป (เช่น LINE) ซึ่งแยก cookie จากเบราว์เซอร์หลัก; เปลี่ยนรหัสผ่านหรือปิดใช้งานผู้ใช้จะเตะ session ทุกเครื่องทันที
- ตาราง `users`, `sessions` (migration `0001`); รหัสผ่านเก็บแบบ scrypt; session เก็บ hash ของ token ใน DB; cookie `httpOnly` + `SameSite=Lax` + `Secure` บน production; ตรวจ Origin กัน CSRF; ล็อก 15 นาทีเมื่อผิด 5 ครั้ง (เก็บในหน่วยความจำ)
- ขอบเขตข้อมูล (ตัดสินจากบทบาท + วิธี login ของ session นั้น): Super Admin เห็นทุกส่วนงาน; **ช่างเทคนิคที่ login ด้วย Username/Password เห็นทุกส่วนงาน ไม่ต้องกำหนดส่วนงาน**; Viewer เห็นเฉพาะส่วนงานของตัวเอง (รวมส่วนงานย่อย); **ทุกคนที่ login ด้วย CMU (ยกเว้น Super Admin) เห็นเฉพาะส่วนงานของตัวเองเสมอ** ผู้ใช้ที่ไม่มีส่วนงานจะไม่เห็นข้อมูล ตอนนี้ดูได้อย่างเดียว สิทธิ์เขียน/แก้ไขจะมาตอนทำฟีเจอร์แก้ข้อมูล
- ตอนนี้ตั้งใจมีบัญชีช่างเทคนิค Username/Password แค่ 1 บัญชี (เพิ่มที่ `/users`) ระบบยังไม่บังคับจำนวน
- ผู้ใช้ที่เข้าด้วย CMU ครั้งแรกจะเป็น Viewer และระบบเลือกส่วนงานให้จากชื่อคณะที่ CMU ส่งมา (ต้องตรงชื่อ/รหัสส่วนงานเป๊ะ) ถ้าไม่ตรงจะไม่เห็นข้อมูลจน Super Admin กำหนดที่ `/users` ชื่อฟิลด์ตั้งทับได้ด้วย `CMU_OAUTH_ORG_FIELDS`
- ทดสอบ flow CMU กับเซิร์ฟเวอร์จำลองในเครื่องแล้ว (state ผิด, อีเมลนอก @cmu.ac.th, คณะตรง, คณะไม่ตรง)
- API ข้อมูลทุกตัวต้อง login แล้ว (เอา `ALLOW_DEMO_DATA` ออกแล้ว)
- บัญชีทดสอบในเครื่อง (`npm run db:seed`) รหัสผ่านทุกบัญชี `dev-password-1234` (เฉพาะ local): `dev-admin` (Super Admin) และ `dev-tech` (ช่างเทคนิค เห็นทุกส่วนงาน) เท่านั้น
- **CMU OAuth ยังไม่ได้ทดสอบกับของจริง**: ต้องขึ้นทะเบียนแอปกับ CMU เพื่อขอ client id/secret และตรวจ URL ที่ค่าเริ่มต้นใน `server/config.ts` (เขียนจากความจำ ยังไม่ได้ยืนยัน) ทุกค่าตั้งทับได้ด้วย env `CMU_OAUTH_*` (ดู `.env.example`) Redirect URI ที่ต้องลงทะเบียน: `https://equiplog.ddns.net/api/v1/auth/cmu/callback`

## 8. ข้อควรระวัง

- Local (MariaDB 10.4) ต่างจากโฮสต์ (10.11): ใช้ `datetime` สำหรับเวลาที่ว่างได้ (ไม่ใช้ `timestamp`) เพื่อไม่ให้ค่าเริ่มต้นเพี้ยน และเขียน SQL ให้ใช้ได้ทั้งสองรุ่น; ควรอัปเดต XAMPP ให้ใกล้เคียงโฮสต์ (backup `C:\xampp\mysql\data` ก่อน เพราะมีฐานข้อมูลอื่น)
- ตาราง `mysql.db` ของ XAMPP เสียหาย (สร้าง user ใหม่พร้อมสิทธิ์ไม่ได้) จึงใช้ `root` ในเครื่อง
- Apache ของโฮสต์ cache ผลลัพธ์ที่มี `s-maxage` จึงตั้งหน้าเป็น dynamic + `no-store` (อย่าเอาออก)
- ห้ามส่งรหัสผ่านฐานข้อมูลในแชท ใส่ในช่อง Environment variables ของ DirectAdmin หรือ `.env.local` เท่านั้น
